# AI 導入指引

給在專案裡工作的 AI 代理人看的。專案已經用 submodule 掛上 quality-referee（`tools/referee/`），要你把三道關建立起來時，照這份做。專案可能完全沒有測試，從零開始也適用。

人要看的導入說明在 [README.md](../README.md) 的「安裝到專案」。記分表和設定檔的規則在 [合約.md](合約.md)。

## 不能做的事

這幾條比任何步驟都優先。做不到目標時停下來回報，不要用下面的方式讓檢查通過：

- 不改門檻、`gates`、`exclude`、`tests`、排除清單（`.referee.json`、`.referee-equivalents.json`），也不改 `tools/referee/`、CI 設定、`.claude/`。認為設定該調整時，寫出理由交給人決定。
- 不刪除、註解掉、跳過既有的測試，不把斷言改鬆。
- 測試的正確答案不能從程式的輸出抄來當成「需求」。從現有行為抄來的答案要標明（見「替舊程式補測試」）。
- 不為了覆蓋率寫沒有斷言的測試。只呼叫、不檢查結果的測試會讓第二關過，第三關抓錯率會掉，而且沒有驗證任何事。
- 不用「條件不成立」的案例湊覆蓋率。要測一個分支，就要有讓那個分支的條件成立的案例。例如某個折價券只在特定日期有效，而你控制不了日期：只測「金額不夠所以折 0 元」這種哪一天都成立的案例，那一行會被算成有覆蓋，第二關可能就過了，但日期的判斷完全沒被驗證。條件成立的那一邊測不到，就照「測試寫不出來的時候」回報。
- 不為了測試去改正式程式的行為。需要改結構才測得到時，照「測試寫不出來的時候」處理。

## 先看現況

在專案根目錄：

```
git submodule update --init
ls -a .referee.json .referee-equivalents.json .claude/hooks/gate.sh
```

設定檔和 hook 不在的話，照 README「安裝到專案」複製 `tools/referee/templates/<語言>/` 的範本，再依專案調整 `.referee.json` 的 `sources`、`tests`、`exclude`、`test.command`。複製範本和第一次調整設定是導入的一部分，要讓人看過；之後就不要再動。

接著量一次整個專案（不帶 `--base`）：

```
python tools/referee/referee.py test
python tools/referee/referee.py crap
```

讀結果時注意：

- **完全沒有測試的專案，第一關會通過。** `dotnet test`、`go test ./...` 在沒有任何測試時結束碼都是 0。「第一關通過」不代表有測試，要看測試專案或測試檔在不在。
- `crap` 的表格是待辦清單：覆蓋率 0% 的函式都還沒有測試，由上往下是風險高到低。把這張表留給人看（`--json` 可以存檔）。
- 複雜度低的函式沒有測試也不會超標（例如複雜度 3、覆蓋率 0% 剛好是 12 分）。不要只看 PASS 或 FAIL，要看覆蓋率那一欄。

## 建立測試骨架

專案沒有任何測試時，先建一個跑得起來的測試專案，放一個真的測試，確認三個指令都動得了，再開始補。

### C#（SDK 風格、.NET 6 以上）

```
dotnet new xunit -o <專案名>.Tests
dotnet sln add <專案名>.Tests
dotnet add <專案名>.Tests reference <專案名>
```

- 測試專案的目錄名稱要對得上 `.referee.json` 的 `tests`。範本比對 `*.Tests/`、`*.Test/`、`*.UnitTests/`，對不上的話測試程式會被當成正式程式來量。
- `dotnet new xunit`（`mstest`、`nunit` 也是）建出來的專案已經引用 `coverlet.collector`，檢查員靠它算覆蓋率。既有的測試專案沒有引用時要加上。
- 專案沒有 `.sln` 或 `.slnx` 時先建一個（`dotnet new sln`）並把所有專案加進去，或在 `.referee.json` 兩個 `inspector` 指令加 `--target <專案檔>`。
- 刪掉範本附的空測試（`UnitTest1.cs`）。
- 舊式 .NET Framework 的 csproj 不支援，遇到時回報，不要硬轉。

### Go

測試檔和被測的程式放同一個目錄，檔名 `<名稱>_test.go`。測試分散在別的套件時，兩個 `inspector` 指令都加 `"--coverage-scope", "module"`。

### 其他語言

沒有標準檢查員。回報給人，由人決定要不要照 [合約.md](合約.md) 寫自訂檢查員；不要自己挑一個量法就開始。

## 替舊程式補測試

舊程式通常沒有寫下來的需求，測試只能先記錄「現在的行為」。這種測試有用（之後改壞會被抓到），但它不能證明現在的行為是對的，現有的錯誤也會被當成正確答案鎖進去。所以：

1. **照 `crap` 的表由上往下補**，一次處理一個函式或一個檔案，補完就跑 `test` 和 `crap` 確認數字有動。
2. **答案的來源要分清楚。** 有需求、規格、文件、註解、呼叫端可以對照的，答案照那些寫。只能從現有行為得到的，在測試上標明，例如測試名稱或註解寫「記錄現有行為，待確認」，並在回報裡列出來給人核對。
3. **看起來像錯誤的行為不要順手修，也不要寫成正確答案後不講。** 照現況記錄，在回報裡指出來。
4. **每個分支都要有會失敗的斷言。** 邊界值兩邊各一個案例（例如門檻是 1000 就測 999 和 1000）。
5. **用第三關檢查自己寫的測試。** 補完一批就跑 `mutation`（範圍見下一節），看「沒抓到」和「測試沒跑到」的清單，補到抓得到為止。

## 第三關的範圍

抓錯檢查很慢，範圍越大越久。導入時：

- 平常改程式用 `mutation --base <base>`，只算這次改到的行。
- 替舊程式補測試時，正式程式沒有改，`--base` 會回報「沒有改到正式程式碼」，第二關也一樣回報「沒有改到任何函式」，兩關都直接通過。這個通過不代表測試夠了。要檢查補的測試，第二、三關都不帶 `--base` 跑整個專案，或請人決定先量哪些目錄。
- **除了兩個比例，每個函式至少要有一個改壞的版本被抓到。** 沒做到的函式會列在「沒有任何改壞的版本被測試抓到的函式」底下，這一關就不過。括號裡「測試沒跑到」多，是這個函式沒有測試；「沒抓到」多，是測試有跑到但沒有檢查結果。
- 這條規則只要求一個，過了不代表測試夠。仍然要讀「沒抓到」和「測試沒跑到」的清單，補到兩個比例都穩穩過門檻。
- 被列出來的函式補不了測試時，不要為了讓它消失去加一個不檢查結果的呼叫，照「測試寫不出來的時候」回報。
- 認為某個改壞版本改了也沒差時，寫出理由交給人。排除清單要人核准，你不能自己加。

## 測試寫不出來的時候

照上面做還是補不起來，通常不是測試的問題，是程式的結構讓它沒辦法被單獨執行。這本身就是要回報的結果。常見的情況：

| 現象 | 原因 | 要怎麼改才測得到 |
|---|---|---|
| `crap` 標「要拆函式」 | 函式太大，光靠覆蓋率壓不到門檻以下 | 拆成幾個小函式，各自測 |
| 函式裡直接讀時鐘、亂數、環境變數 | 每次執行結果不一樣 | 把值當參數傳進來，或透過介面取得 |
| 函式裡直接建立資料庫、HTTP、檔案系統的物件 | 測試一跑就會碰到外部系統 | 依賴反轉：依賴介面，由呼叫端傳入實作 |
| 靠靜態或全域的可變狀態 | 測試之間互相影響，沒辦法單獨準備狀態 | 把狀態收進物件，由呼叫端傳入 |
| 建構式裡做實際的工作（連線、讀檔） | 連物件都建不起來 | 建構式只收依賴，工作移到方法裡 |
| 計算和輸出入混在同一個函式 | 要測計算就得連輸出入一起跑 | 把計算抽成沒有副作用的函式 |

一個函式常常只有一部分測不到：前半段是單純的檢查和計算，後半段才碰到時鐘或外部系統。這時能確定測的分支照樣補，測不到的分支逐一列進回報。這個函式在 `crap` 的表格裡會繼續超標，照實寫，不要為了讓它過關去湊覆蓋率。

遇到時這樣處理：

1. **不要硬測。** 不用反射去碰私有成員或重設靜態狀態、不用會改寫執行環境的工具去攔截靜態呼叫、不讓測試真的去寫檔案或連外部系統、不讓測試的結果取決於執行的日期時間或測試之間的先後順序。
   - 靜態或全域狀態的例外：只透過公開的介面操作，而且每個測試用自己專屬的資料（例如各自的代碼），不管單獨跑、一起跑、照什麼順序跑結果都一樣，這樣可以補。但結構問題還是要回報，並寫明這種測法的代價：測試靠哪些行為才準備得了資料、哪些初始狀態因此沒有驗證。
2. **停下來回報**，每個函式一筆：位置、屬於上表哪一種、建議怎麼改、改動會影響哪些呼叫端。
3. **人同意之後才改結構**，而且和補測試分成不同的 commit。改之前先替改得到的部分補測試；改的時候只動結構，不動行為。

## 交給人的事

三道關只判斷數字，下面這些要請人做，回報時列出來提醒：

- 審測試：正確答案是不是照需求寫的，特別是標了「記錄現有行為」的那些。
- 把規則鎖起來：CODEOWNERS 指定 `.referee.json`、`.referee-equivalents.json`、`.gitmodules`、CI 設定、`.claude/` 由誰審核；main 分支保護要求三關全過、至少一人核准；AI 用的帳號不給合併權限。
- 決定門檻（CRAP 最寬只能到 30）和第三關的範圍。
- 核准排除清單的每一項。

## 做完的標準

看你做的是哪一種工作：

- **平常改程式**（有改到正式程式）：`python tools/referee/referee.py check --base <base>` 結束碼 0。
- **從零建立測試、替舊程式補測試**（沒有改正式程式）：`check --base` 一定會通過，不能拿它當依據。以不帶 `--base` 的結果為準：
  - `test` 結束碼 0，而且專案裡真的有測試。
  - `crap` 和 `mutation`（都不帶 `--base`）結束碼 0；或者還沒過的每一項都列在回報裡，說明是排在後面，還是測試寫不出來。
  - 只要整個專案的 `crap` 或 `mutation` 還沒過，回報的第一句就要寫「導入還沒完成」，並提醒人：這個分支在 CI 上會三關全過，原因是沒有改到正式程式，不是測試已經夠了。

不論哪一種，回報都要有：

- 整個專案的 `crap` 表格，還沒有測試的函式列得出來，每一個都有說明：已補、只補了一部分（列出沒測到的分支）、排在後面、或是測試寫不出來（附上面那種回報）。
- 標了「記錄現有行為」的測試、看起來像錯誤的行為、要人決定的事，都列在回報裡。

還沒做到的部分照實寫，不要因為三關通過就說導入完成。
